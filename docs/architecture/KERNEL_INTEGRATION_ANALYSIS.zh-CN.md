# 内核集成必要性分析

日期：2026-09-28。范围：仅做分析。本轮没有引入驱动、内核钩子、服务、注册表或启动设置，也没有引入安装程序。根目录的目标设计规定，只有在测量证明必要时才考虑内核集成。

## 证据

Windows 原生探针使用 `PlatformTickDriver`、真实遥测、受控子进程和控制器读回。此前的 GPU 路由结果已经**撤回**：修复前的特征构造器把缺失的 GPU/NPU 利用率错误地填成零。修复后，2,000 次控制周期调用产生 823 次受控进程操作；第 99 百分位耗时为 1.2307 毫秒，最大耗时为 1.8938 毫秒，对照 20 毫秒的调用预算没有超时。设备利用率不可用时，GPU 模型绑定正确地拒绝执行。独立的 DirectML 队列在 GPU 上执行了策略模型；显式选用的实验性 QDQ 候选模型在 NPU 上执行了所有已分析节点，耗时约 680 毫秒。该候选模型在 1,000 个合成样本中有 16 个最高分标签不一致，因此不能认定与生产模型等效。

这些样本未计入测试程序的休眠时间，也未测量完整守护进程的状态、事件和 IPC 写入延迟、持续竞争或热负载。它们不能证明最坏情况或硬截止期限。原生优先级、亲和性和精确的电源方案接口在用户态工作，操作后恢复了原始状态。

## 决定

目前没有测量到必须引入内核代码才能解决的失败。平台操作继续留在适配器之后，同时保持慢侧有界准备、不可变策略交接、过期控制和安全模式。厂商利用率缺失、生产 NPU 模型准确率、第二登录用户的 ACL 覆盖，以及代表性应用效果数据，都不能仅靠把核心层放进驱动来解决。

Windows 调度可抢占，并受竞争线程、中断和其他负载影响。在宣称硬截止期限之前，需要更大的负载与温度样本，以及端到端延迟预算。如果今后某项已接受的需求经测量确实无法用用户态接口满足，应先记录具体缺口、权限与签名及部署成本、恢复方法和平台矩阵，再单独决定是否引入内核组件。本分析没有实现驱动。

泛化的自主工具代理执行仍是另一项设计决策：当前意图契约没有规定工具模式、逐工具身份与授权、取消、副作用回滚和评估。现有本地意图共识只协调有界的分类建议，不等于任意工具协作。
